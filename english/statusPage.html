Grafana Status Page - MessMass

This project was carried out during my final internship within the MessMass team at Michelin. The objective was to design and implement a status page for real-time monitoring of the company's critical middleware through an intuitive dashboard built with Grafana and powered by Prometheus. Over 24 weeks, the solution evolved from a simple proof of concept to a rich tool presenting the statuses of fifteen internal and external middleware, incident history, service quality indicators (SLI/SLO), and deep access (drill-down) for diagnostics.

Context and objectives

As part of the OneSystem IT Platforms program, the MessMass team sought to improve the observability of its middleware (EDA, MFT, EAI, IFE/M2I, ETL). The status page had to meet several objectives: provide a synthetic view of service states, quickly detect failures, monitor service levels, and offer access to detailed information without overloading the interface. The solution also had to integrate into the existing ecosystem (Grafana, Prometheus, ServiceNow) and respect graphic standards to be easily adopted by other teams.

Key features

  • Real-time monitoring of fifteen internal and external middleware via Prometheus and various exporters (Blackbox, OpenTelemetry, custom scripts).
  • Clear visual indicators: global status (OK/KO/Maintenance), standardized colors and icons for each service.
  • Incident history with links to ServiceNow tickets and SharePoint tracking pages.
  • Calculation and display of service level indicators (SLI) and SLO burn rate: performance is monitored and compared to objectives.
  • Drill-down function allowing display of detailed component and node lists for middleware, with their individual statuses.
  • Organization by functional domain (EDA, MFT, EAI, IFE/M2I, ETL) to structure the dashboard and facilitate navigation.
  • Integration of data from an internal API to enrich the page with information from other squads.
  • Complete user and technical documentation, graphic standardization guidelines

Architecture and implementation

The status page relies on a flexible observability architecture. Metrics are collected by Prometheus via several channels: the Blackbox Exporter to measure service availability (HTTP, ping), OpenTelemetry collectors to export internal gauges (queue, message count), Python scripts and K6 tests to verify API responsiveness. A REST service also exposes consolidated information in JSON format.

Grafana queries these sources and presents results in custom panels. The first version simply used tables and binary gauges. Successive iterations led to using the Canvas panel to arrange colored and dynamic cards, and combined panels displaying status, history, and SLI simultaneously. PromQL queries calculate statuses and alert thresholds. Links to ServiceNow and SharePoint are generated dynamically.

Project evolution

Development took place in several distinct stages:

  • 1st version - Blackbox Exporter PoC: A simple proof of concept based solely on availability tests with the Blackbox Exporter. Statuses were binary (up/down) and the interface very clean.
  • 2nd version - New statuses and test visualizations: Introduction of more detailed statuses (maintenance, error, warning) and experiments with dynamic blocks in Grafana. This version validated ideas but the layout remained confusing.
  • 3rd version - Domain structuring and API: Reorganization by functional domains (EDA, MFT, EAI, IFE/M2I, ETL) and integration of API team data. Addition of SLI/SLO indicators and ergonomic improvements.
  • Final version - HIP squad validation: Harmonization of colors and icons, addition of an information banner and contextual links. A feedback form was distributed and allowed adjusting SLI format, information relevance, and link placement.

Limitations and perspectives

  • Restricted access: the status page is currently reserved for users with a Grafana account. A considered evolution is publishing a public version with light authentication, or even exporting to a static site accessible to all employees.
  • Status homogenization: each middleware has its own error rules and thresholds. Standardizing indicators and color codes remains a challenge to ensure consistent reading.
  • Test and deployment automation: K6 scripts and continuous integration can be improved to industrialize page updates and new service validation.
  • Scope extension: the methodology and graphic charter could be applied to other DOTI squads or external services (database, network) by adapting collectors and indicators.

Concepts used

  • Grafana for visualization and panel arrangement.
  • Prometheus and its exporters (Blackbox, OpenTelemetry) for metric collection and exposure.
  • K6 for load testing and API response time evaluation.
  • Canvas panel, table panel and other Grafana plugins for building interactive maps.
  • Python, Shell and REST API for data aggregation, transformation and exposure.
  • Writing user and technical documentation, creating a graphic charter guide to standardize the page.
